调度器三连开篇，讲默认调度器架构。核心一句话：调度 = Predicate（预选/过滤）+ Priority（优选/打分）+ Bind（绑定 nodeName）。两个控制循环：Informer Path 监听 Pod/Node 变化喂调度队列和 Scheduler Cache；Scheduling Path 从队列出队 Pod，跑 Predicate 过滤节点，跑 Priority 打分 0-10，得分最高的节点填充 Pod.spec.nodeName。三个性能优化我认同是关键：Cache 化（缓存集群信息避免算 Predicates 时反复拿数据）、乐观绑定（Assume 先更新 cache 再异步写 APIServer，kubelet 端 Admit 二次确认兜底）、无锁化（Predicate/Priority 并发执行不加锁，只有队列和 cache 操作加锁且不在算法路径上）。

我的判断：默认调度器是 K8s 最后一个没暴露良好扩展接口的组件，这不是疏忽是历史债——早期优先服务公有云需求，私有云大规模复杂场景下通用调度器不够用。Scheduler Framework 是正解，把调度生命周期各关键点暴露成 Go plugin 插入点，让社区自定义。对比 Yarn/Mesos：Mesos 是两级调度（框架自己决定资源怎么用），K8s 默认调度器是单级集中式（调度逻辑全在 kube-scheduler），通用性好但定制性差，所以才有 Volcano/Kube-batch 这类调度器扩展做 AI/批处理场景。Go plugin 机制要求编译期选插件是个硬伤，不能热加载，生产环境要么 fork 要么走调度器框架的扩展点。
