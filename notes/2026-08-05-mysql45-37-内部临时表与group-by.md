丁奇第 37 讲。内部临时表（优化器自己建的，用户看不见）典型场景：group by 无索引可用时。流程：建内存临时表（主键是 group by 字段）→ 全表扫，每行尝试插入临时表，主键冲突就更新聚合值 → 内存不够转磁盘临时表（8.0 前 MyISAM，8.0 用 InnoDB）。优化原则：group by 结果不需要排序就加 **order by null**（省 filesort）；能用索引就别让临时表出现；tmp_table_size 调大避免落盘；数据量实在大用 SQL_BIG_RESULT 直接走排序算法。

**对我的价值**：explain 里的 **Using temporary** 是 group by 性能问题的第一信号。很多人只盯 Using filesort，其实 temporary 出现就说明优化器放弃了索引有序性，走了「建临时表聚合」这条重路径。order by null 是个冷门但立竿见影的优化——group by 默认对结果排序，不要排序就显式声明，省一次 filesort。

**立场**：内部临时表的存在说明一个事实——**SQL 的声明式语法和物理执行之间隔着优化器的「创造性翻译」**。你以为写的是聚合，它执行的是建表+插入+更新+排序。理解这层翻译，才能写出「优化器好翻译」的 SQL。这也是我为什么反对在 SQL 里写复杂业务逻辑——翻译层一旦复杂，行为就不可预测。
