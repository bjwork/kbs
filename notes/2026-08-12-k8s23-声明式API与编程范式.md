kubectl create + kubectl replace 是命令式（用新对象替换旧对象），kubectl apply 才是声明式（对 API 对象做 PATCH，支持多写端 Merge）。声明式 API 三层含义：声明期望状态、多端以 PATCH 修改、控制器自动调谐实际状态向期望状态收敛。Istio 的 Envoy 自动注入就是声明式 API 的典型用例：用 Dynamic Admission Control（Initializer）拦截新建 Pod，用 TwoWayMergePatch 把 Envoy 容器定义合并进用户提交的 Pod YAML，用户完全无感。

**我的判断**：声明式 vs 命令式是 K8s 的根本范式革命，所有 kubectl 都是声明期望状态。这个思想对 AI workflow 编排也有启发——LangChain/AutoGen 现在还是命令式（一步步调 run），如果改成声明式（声明「我要一个能查知识库的回答」，系统自己 reconcile 到合适的 agent 组合），可观测性和可重入性会好得多。Istio 的 Initializer 注入是声明式 API 威力的最佳展示：用户写普通 Pod YAML，系统自动「加工」成带 sidecar 的版本，这种「声明意图、系统加工」的模式正是声明式的精髓。不过要注意，Initializer 后来在 K8s 里被 mutating webhook 取代了，但思想一脉相承。PATCH 支持「多写端并发改同一对象不冲突」这点，是 K8s 能承载 Istio 这种「在 K8s 之上再建一层控制平面」的根本——没有声明式 PATCH，Service Mesh 这类扩展层根本建不起来。
