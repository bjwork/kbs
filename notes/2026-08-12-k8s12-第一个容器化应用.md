这篇是开发者视角的 K8s 入门。核心转变：从 `docker run` 命令行到 YAML 声明式 API。一个 Deployment YAML 包含 metadata（Labels 是过滤依据）、spec.replicas（副本数）、spec.template（Pod 模板）、selector.matchLabels（控制器靠它找到被管 Pod）。操作统一用 `kubectl apply`——不管创建还是更新都走它，K8s 自己 diff 决定动作，这比 `kubectl create/replace` 更贴合声明式语义。

几个实战要点：`kubectl describe pod` 的 Events 是 Debug 第一现场（调度、拉镜像、启动全记录在这）；Volume 是 Pod 级字段，容器用 volumeMounts 声明挂载哪个 Volume，emptyDir 是临时目录、hostPath 是显式宿主机目录；滚动更新时新旧 Pod 交替创建删除。思考题答案：replicas=1 的 Deployment 比裸 Pod 强在——Pod 挂了 Deployment 会重建，裸 Pod 不会自我修复。

**我的判断**：这篇点破了 K8s 对开发运维协作的改造——**YAML 文件成为沟通媒介**。容器镜像保证应用本身一致性，YAML 保证部署参数一致性，git diff 能看到部署变更，这比口口相传的运维文档可靠太多。对后端的启发是：写应用时就要想好它会被编成什么 API 对象，健康检查端点、优雅退出、配置外部化（ConfigMap）这些得在代码里预留。从 docker run 到 kubectl apply 这道坎必须过，过了之后回头看 Docker 命令行更像调试工具而非部署方式。
