丁奇第 14 讲。MyISAM 表存行数所以 count(*) 飞快；**InnoDB 因为 MVCC，每行对不同事务可见性不同，只能一行行数**——这是为一致性付的代价。优化器会选最小的索引树来扫（聚簇索引太大）。count 语义排序：count(*) ≈ count(1) > count(主键) > count(字段)。业务方案对比：Redis 计数（两个存储没有分布式事务，一致性视图拿不到，会出「计数和最新列表对不上」的逻辑矛盾）；**单独建计数表放 MySQL 里**（利用事务原子性，同一事务里更新数据表+计数表，正确且够用）。

**对我的价值**：「Redis 计数为什么不对」的论证过程值得细品——不是技术不能，是**两个独立存储构成不了一致性视图**。无论你先更新 Redis 还是先插 MySQL，总有一个时刻读到的计数和明细来自不同时间点。这个推理模式可以推广到所有「要不要把状态放第二个存储」的决策。

**立场**：作者最后落在「把计数留在 MySQL 用事务保证」，务实。但我补一个他没展开的场景：**计数表自己会成热点的**——全站总览页每秒几千次 count 查询打在同一张计数表上，照样要缓存。正确姿势是 MySQL 计数表做 source of truth，Redis 做它的只读缓存并接受短暂不一致，而不是拿 Redis 当真相。
