丁奇第 15 讲，前 14 讲的评论答疑合集。核心问题串：①binlog 三种格式（statement 记原文有主从不一致风险 / row 记行变更安全但量大 / mixed 自动选）；②什么算「备库延迟」——seconds_behind_master 的口径是「relay log 应用落后」，不是单纯网络延迟；③force index 之后发现索引选对了但还是慢，可能是回表代价没算清；④覆盖索引不是「建一个把所有列都包进去的大索引」，是为**特定高频查询**定制的。思考题给了一个有趣的边界：update t set a=a+1 where id=1 这种「值自增」语句，statement 格式 binlog 在备库重放时结果可能不同。

**对我的价值**：答疑文章最容易跳过，但这篇把 binlog row vs statement 的选择逻辑讲透了——statement 省空间但「同一条 SQL 在主备执行结果可能不同」（带 limit 不带 order by、用 uuid() 等非确定性函数），row 格式把结果钉死。现在 5.7.7+ 默认 row，这个争论基本是历史，但**老系统迁移时 binlog_format 检查**仍在我的 checklist 上。

**立场**：丁奇回答评论区问题的认真程度（每个「好问题」都展开）提醒我：技术问答的价值不在答案本身，在**提问者暴露的认知盲区模式**。这篇里多数人卡在「以为统计信息是精确的」「以为覆盖索引是建大宽索引」——都是把估算当真理的惯性。我自己犯过同款错误。
