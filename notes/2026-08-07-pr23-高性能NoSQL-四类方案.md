关系型数据库的四个缺陷对应四类 NoSQL 方案——**NoSQL 不是替代 SQL，是补充（Not Only SQL）**，每个优势都是牺牲 ACID 的某个特性换来的。

**K-V 存储（Redis）**：解决「行记录无法存数据结构」的问题。Redis 的 Value 可以是 string/hash/list/set/sorted set/bitmap/hyperloglog，所以叫「数据结构服务器」。例如 LPOP 用 MySQL 模拟要维护位置编号、查首行、删首行、批量更新位置——性能极差。代价：**不支持完整 ACID**，Redis 事务只保证 I 和 C，不保证 A 和 D。但微博关注数丢一两条无感，按业务特性取舍。

**文档数据库（MongoDB）**：解决「schema 强约束」问题。JSON no-schema，新加字段不用 DDL、历史数据不出错、复杂结构一个文档搞定。特别适合电商/游戏（不同商品属性差异巨大）。代价：**不支持事务 + 不支持 join**——库存+下单这种强事务场景不能用。

**列式数据库（HBase）**：解决「大数据分析 I/O 高」问题。行式存储读一行所有列；列式只读需要的列（1KB 行只取 4 字节体重）。压缩率 8:1~30:1（行式只有 3:1~5:1），因为单列相似度高。代价：**多列更新时变随机写、且要解压再压缩再写回**——所以只能用于离线分析，不适合在线更新。

**全文搜索引擎（Elasticsearch）**：解决「like 模糊匹配全表扫描」问题。核心是**倒排索引**——建立「单词→文档」的索引，正排索引则是「文档→单词」。ES 把所有字段默认建倒排索引，所以任意条件组合都快。使用方式：把关系型数据转成 JSON 文档再喂给 ES。

**立场**：四类方案对应四个缺陷，这个映射记牢就不会再纠结「为什么有了 MySQL 还要 Redis/Mongo/HBase/ES」。「NoSQL 是补充不是替代」这个判断在 AI 时代依然成立——向量数据库（Milvus/Qdrant）本质上也是同一逻辑：解决关系型存不了 embedding 的问题，但 ACID 一样不行，还是做补充用。
