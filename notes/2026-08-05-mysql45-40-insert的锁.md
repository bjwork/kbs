丁奇第 40 讲。普通 insert 很轻量（自增锁拿到值就释放），但特殊情况锁很多：①**insert ... select**——可重复读下，select 的表扫描到的记录和间隙全加读锁（为了 binlog 一致性）；如果 insert 和 select 是**同一张表**，会循环写入，要借助临时表；②**唯一键冲突**——insert 检测到冲突时，会在冲突值上加**共享 next-key lock（S 锁）**，两个事务同时 insert 相同唯一值会互等 S 锁死锁；③insert ... on duplicate key update 的锁语义更复杂。

**对我的价值**：「唯一键冲突加 S 锁」是死锁的经典来源——事务 A insert 值 X（成功，持 X 的插入意向锁），事务 B insert 值 X（冲突，申请 X 的 S 锁等 A），事务 A 再 insert 值 X 的相关记录（要等 B 的 S 锁释放）→ 死锁。解法：**冲突后立即提交或回滚，别在事务里继续操作**。这也是为什么批量 insert 建议按唯一键排序——减少交叉等锁的概率。

**立场**：insert ... select 的锁范围（select 的表全加读锁）很多人不知道，导致「我就 copy 一下数据怎么把线上表锁了」。可重复读下这是为了保证 binlog 重放时 select 的结果和主库一致——又是「可重复读的语义成本」。再次印证我的立场：**RC + row binlog 是普通业务的最优解**，可重复读的这些边角规则只有 DBA 需要精通。
