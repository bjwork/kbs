编程的本质是确定性，架构设计的本质是**不确定性**——同一系统 A/B 公司设计出来不一样都能跑，没有语法级的对错约束。所以架构师容易陷入选择困境，三原则就是应对这种不确定性的方法论。

**合适原则**：「合适优于业界领先」。三个失败根源——没那么多人想做那么多事（将军难打无兵之仗）、没那么多积累想一步登天（罗马不是一天建成）、没那个业务场景幻想灵光一闪（冰山下面才是关键，业界领先方案都是业务逼出来的）。所以 BAT 架构师去小公司经常翻车——不是技术不行，是平台、资源、积累都没了。

**简单原则**：「简单优于复杂」。软件里复杂代表问题，不代表先进。复杂性有两类——**结构复杂**（组件多，故障率乘性叠加：3 个组件 72.9%、5 个 59%）和**逻辑复杂**（单组件功能太多或算法太复杂）。KISS 原则在架构层同样成立。心跳方案 vs ZooKeeper 主备决策，用心跳不是「不高级」，是「更合适」。

**演化原则**：「演化优于一步到位」。软件跟建筑形似神不似——建筑建成即永恒，软件**变化才是主题**。Windows 1.0 和 Windows 8 已经是两个系统。正确姿势像生物演化：满足当时业务需要、在运行中迭代修复、业务变化时扩展/重构/重写，但保留有价值的经验和设计。

**立场**：这是我心里整个专栏最重要的一篇。三原则互相印证——合适是目标、简单是手段、演化是路径。我在做 AI 应用架构时常提醒自己别一上来就上 LangChain + 向量库 + Agent 编排的「复杂正确」，而是先用最简单的 prompt + 单次调用跑通业务，这就是「合适+简单+演化」的实际运用。
