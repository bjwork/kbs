Projected Volume（投射数据卷）是「把预定义数据投射进容器」的特殊 Volume，四种：Secret（加密数据，如数据库凭证，Base64 转码非加密，生产要开加密插件）、ConfigMap（非加密配置，如 .properties）、Downward API（让容器拿 Pod 自己的 metadata：name/namespace/labels/IP）、ServiceAccountToken（特殊 Secret，自动挂到 `/var/run/secrets/kubernetes.io/serviceaccount`，Pod 里跑 K8s 客户端用 InClusterConfig 拿授权，最省事）。环境变量方式拿这些信息没有自动更新能力，Volume 方式 kubelet 会定时同步（有延时，应用层仍要写重试）。

健康检查两条线：**livenessProbe** 决定容器要不要重启（exec/httpGet/tcpSocket，失败触发 restartPolicy 重建容器，注意 K8s 没有 Docker stop 语义，重启=重建）；**readinessProbe** 决定 Pod 能不能被 Service 转发流量，不影响生命周期。两者用途不同——liveness 管「活着」，readiness 管「能接活」。restartPolicy 默认 Always，还有 OnFailure（仅异常重启）和 Never（不重启，用于要保留退出上下文的场景）。Pod 恢复只在当前节点发生，不会跨节点迁移——所以裸 Pod 宿主机挂了不会自愈，必须用 Deployment 管理才有迁移能力。

PodPreset：运维预定义 selector + 要追加的字段（env/volumeMounts/volumes），开发提交简单 Pod YAML 时 K8s 自动注入，降低开发门槛。多 PodPreset 作用同一 Pod 时冲突字段不修改。

**我的判断**：livenessProbe 对 Java Web 特别关键——JVM 还在但应用线程死了（如线程池满、死锁）是 Running 却不 Ready 的典型，靠 docker 看进程在不在根本发现不了。initialDelaySeconds 设不好会误杀慢启动应用（Spring Boot 起动 30s+ 是常态），这个值要按应用实际启动时间设。Secret 默认只 Base64 是安全陷阱，生产必须开 etcd 加密。对 AI 场景，ServiceAccountToken + InClusterConfig 让训练任务里的代码能直接调 K8s API（比如拉配置、上报状态），省掉外部凭证管理。
