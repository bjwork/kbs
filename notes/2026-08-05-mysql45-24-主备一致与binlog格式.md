丁奇第 24 讲。binlog 三种格式：statement（记 SQL 原文，省空间但非确定性函数/limit 无 order by 会主从不一致）、row（记每行变更前后值，安全但量大，5.7.7+ 默认）、mixed（自动选，但判断逻辑有坑）。主备流程：主库写 binlog → 备库 IO 线程拉 binlog 写 relay log → SQL 线程回放。主备延迟的本质是**备库消费 relay log 的速度**。高可用方案（MHA、MGR、半同步）全部建立在 binlog 这条链路上。

**对我的价值**：row 格式为什么安全——它记的是「这行从什么改成什么」，不依赖执行环境。statement 的死穴是非确定性：uuid()、now()、found_rows() 这些函数在备库重放时值不同。我现在审 SQL 有个本能反应：**凡是写结果依赖「执行时刻状态」的语句，都在 statement 格式下判死刑**。这也逼着写 SQL 时保持确定性，是个好的副作用。

**立场**：binlog 是 MySQL 生态最大的资产—— Canal、DTS、Flink CDC 全部建立在解析 binlog 上。但 row 格式的代价（大事务 binlog 暴涨、磁盘占用、网络带宽）作者讲得轻了。我见过一个 100GB 的大事务直接把备库 relay log 磁盘打满，复制中断。教训：**大事务拆小**不仅是锁问题，也是复制链路健康问题。row 是正确选择，但得配「大事务监控」这道护栏。
