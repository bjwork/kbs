K8s 编排的核心就一个模式——控制循环（control loop）：`for { 实际状态 := 从集群获取; 期望状态 := 从 YAML/Etcd 获取; if 实际==期望 { 啥也不做 } else { 调谐到期望 } }`。实际状态来自 kubelet 心跳、监控系统、控制器主动收集；期望状态来自用户提交的 YAML。这个调谐过程叫 Reconcile，循环叫 Reconcile Loop 或 Sync Loop。kube-controller-manager 是一堆控制器的集合（deployment/replicaset/statefulset/daemonset/job/cronjob/...），每个都遵循这个模式，差异只在具体业务逻辑。

控制器模式的本质是「用一种对象管理另一种对象」：控制器对象定义期望状态（replicas=2）+ PodTemplate（被控制对象的模板），被控制对象靠 ownerReference 回指拥有者。Deployment 的 template 字段就是一个 PodTemplate，所有被管理的 Pod 都据它创建。统一框架下，不同控制器设计不同逻辑达到不同编排效果。

**我的判断**：这个思想可迁移到任何分布式系统，不限于 K8s。期望状态 vs 实际状态的持续调谐，比事件驱动（event-driven）更鲁棒——事件驱动依赖每个事件都被正确处理，丢一个就漂移；控制循环不关心中间发生了什么，只关心「现在实际是不是期望」，天然自愈、幂等、最终一致。我做过的工作流引擎、配置下发系统，回头看都是控制循环的特例，只是当时没抽象出来。后端设计分布式协调逻辑时，优先想「能不能写成 reconcile loop」——能写成就别用事件链，可观测性和容错性都高一截。这也是 Operator 模式的根基：把领域知识塞进一个控制循环，就能用 K8s 的方式管理任何有状态应用。
