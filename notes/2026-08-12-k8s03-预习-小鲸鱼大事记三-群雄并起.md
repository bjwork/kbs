2014-2015 容器生态的格局：Docker 公司发 Swarm 走「原生 Docker API」路线，Mesos+Marathon 走「万台集群调度」路线，CoreOS 的 rkt 和 Fleet 基本没起来，RedHat 只剩 OpenShift 一张牌。Fig 项目（后来的 Compose）第一次提出「容器编排」概念，被 Docker 收购——这是「docker-compose up」至今仍在用的祖传命令。

我对 Swarm 的「原生 API」策略有保留意见。表面上 `docker run -H Swarm地址` 很优雅，开发者零学习成本，但这是把单机思维硬塞进集群场景的偷懒方案。集群调度的复杂度不会因为 API 长得像单机就消失，Swarm 后来的失败证明：编排系统需要的是对分布式语义的重新建模，而不是把单机 API 加个代理。

Mesos 的两层调度其实更接近正确答案——把资源调度和任务调度解耦，这也是后来 K8s 的 Scheduler + Controller 模式的思想源头之一。但 Mesos 根在 Hadoop 生态，对长-running 服务和有状态应用支持弱，这是它最终没能在容器编排上赢的原因。这一篇末尾 Google 亮出 Kubernetes，才是真正的变量。做后端架构选型时，看一个系统能不能赢，不能只看它现在多强，要看它的思想源头是否来自大规模生产验证——Borg 在 Google 内部跑了十年，这个底气 Swarm 和 Mesos 都没有。
