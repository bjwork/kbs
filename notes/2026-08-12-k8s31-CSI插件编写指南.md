这篇用 DigitalOcean 块存储 CSI 插件走了一遍完整编写流程。插件代码结构极简：driver.go（gRPC Server 注册三个服务）、identity.go（GetPluginInfo 返回 com.digitalocean.csi.dobs，这就是 StorageClass 的 provisioner 字段来源）、controller.go（CreateVolume 调云 API 建磁盘，ControllerPublishVolume 调 API 挂磁盘到虚拟机）、node.go（NodeStageVolume 格式化设备挂到 Staging 目录，NodePublishVolume 把 Staging 目录 bind mount 到 Volume 目录）。

部署方式有讲究：CSI Node 服务用 DaemonSet（每节点一个，kubelet 直接调用），CSI Controller 服务用 StatefulSet（replicas=1，保证更新时永远只有一个实例运行，避免状态不一致）。关键细节是 mountPropagation=Bidirectional——CSI 插件在容器里执行 mount 操作，必须通过双向挂载传播到宿主机，否则宿主机的 kubelet 看不到挂载。

我的判断：这篇把存储是 K8s 最复杂的一块坐实了。一个 PVC 到 Pod 里可写的持久化目录，要经历 External Provisioner 监听 PVC 调 CreateVolume 建 PV、PersistentVolumeController 撮合 PV-PVC、AttachDetachController 建 VolumeAttachment、External Attacher 监听后调 ControllerPublishVolume 挂磁盘、kubelet 调 NodeStageVolume 格式化+NodePublishVolume 挂目录——五个控制循环+两个 sidecar 协作。作为 Java 后端我联想到我们运维 MySQL/Redis 的痛点：数据卷扩容、快照、恢复全是人肉操作，而 CSI 把这些全标准化了，CreateSnapshot/DeleteSnapshot 也是 CSI Controller 的标准接口。Mount 阶段拆成 NodeStageVolume（格式化到 Staging）+ NodePublishVolume（Staging bind 到目标）两步，是为了支持一个 Volume 被同一 Pod 多次挂载（共享已格式化的设备），这个设计细节体现了工程上的复用思想。
