这篇用 Etcd Operator 讲透了 Operator 的本质：CRD 描述有状态应用（如 EtcdCluster 只需 size 和 version），自定义控制器把运维逻辑编码成软件。Etcd Operator 的流程是：先建种子节点（initial-cluster-state=new），再逐个 etcdctl member add 加入新节点，直到 Pod 数等于 size。它为每个 EtcdCluster 对象起一个独立的 Cluster 控制循环，对比期望 size 和实际 Pod 数做 Reconcile。

我的判断：Operator=CRD+自定义控制器，核心价值是把运维专家知识编码成软件。对比手写运维脚本，Operator 让扩缩容、备份恢复变成声明式操作（改 size 即扩容，建 EtcdBackup 对象即备份），且能自愈。作为 Java 后端我深有感触——我们运维 MySQL/Redis 集群全靠人肉脚本和 runbook，遇到故障靠人判断该不该切主、怎么恢复，而 Operator 把这些决策固化成代码。文章里两个细节值得注意：一是 Etcd Operator 没用 workQueue（早期实现），业务逻辑直接在 EventHandler 里跑，这是反模式；二是 Operator 和 StatefulSet 不是竞争关系，Prometheus Operator 就是在控制循环里创建 StatefulSet 而非 Pod。有状态服务上 K8s，Operator 是正确答案，这也是 CoreOS 那句「软件管理软件」的落地。
