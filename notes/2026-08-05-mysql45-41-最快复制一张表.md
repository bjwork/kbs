丁奇第 41 讲。三种表拷贝方式：①**insert ... select**——简单但可重复读下源表加读锁；②**mysqldump 导出文本再 load data**——不加锁，但要走网络/磁盘中转；③**物理拷贝表空间**（5.6+ 的 transportable tablespace：alter table discard tablespace → 拷贝 .ibd → import tablespace）——最快，大表首选，但只能全表拷、要服务器文件权限、源表要短暂只读。误删表恢复的最快路径：备份恢复到临时库 → 物理拷贝回生产库。

**对我的价值**：「物理拷贝表空间」是很多人不知道的黑科技——它跳过了 SQL 层，直接搬 InnoDB 的数据文件。100GB 的表 insert...select 要跑几十分钟还锁源表，物理拷贝分钟级。局限也明显：**只能整表**，不能「拷贝 2023 年的数据」。所以归档场景还是 insert...select 或导出文本，整表迁移/恢复才用物理拷贝。

**立场**：三种方式的选择标准其实是「**源表能不能停、要拷多少、有没有文件权限**」。作者的对比表很实用，但我要加一条现代约束：**云上 RDS 大多不给你文件系统权限**，物理拷贝直接出局。这也是云数据库的隐性成本——你以为买的是 MySQL，其实买的是「MySQL 的一个子集 + 厂商的运维黑盒」。自建库的自由度在某些时刻是真值钱。
