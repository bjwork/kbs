Namespace 管「隔离」，Cgroups 管「限制」，但两者都有硬伤。Namespace 隔离不彻底：所有容器共享宿主机内核（Windows 上跑不了 Linux 容器），时间、内核参数等不能 Namespace 化，容器改时间宿主机跟着变。Cgroups 的盲区更致命：/proc 文件系统不认 Cgroups 限制，容器里 `top` 看到的是宿主机 CPU 和内存——这就是 JVM、Node.js、Python 在容器里误判资源的根因。

张磊强调「容器是单进程模型」：PID=1 的进程就是应用本身，一个容器跑不了两个独立应用。这点跟传统虚拟机思维冲突最大——Java 后端习惯一个机器跑 Nginx + JVM + MySQL 三个服务，塞进容器就得拆成三个容器（后来 K8s 用 Pod 解决这个问题）。用 systemd/supervisord 当 PID=1 来跑多应用是反模式，因为容器和应用要同生命周期，否则「容器活着但应用挂了」编排系统没法处理。

对生产的启示：第一，容器不是安全沙盒，别直接暴露公网，要上 Kata Containers 这类基于虚拟化的安全容器；第二，/proc 误导问题用 lxcfs 修，或者直接用 Java 8u191+ / Java 11+（默认认 Cgroups）；第三，做 AI 训练任务时，单容器单进程模型意味着 GPU 驱动、训练框架、数据预处理要拆成独立容器，用 Pod 编排，而不是塞进一个镜像。这是后面 Pod 设计模式的认知基础。
