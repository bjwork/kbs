这一篇是白话容器基础的总结篇，把前三个零件组装起来：容器进程跑在 Namespace+Cgroups 构成的隔离环境里，文件由联合挂载的 rootfs 层提供，Volume 用绑定挂载（bind mount）把宿主机目录塞进容器。两个关键技术点值得记：docker exec 的原理是 setns() 系统调用，通过 `/proc/[PID]/ns/` 下的 Namespace 文件加入已有容器；Volume 的绑定挂载是 inode 替换，挂载点 /test 的 dentry 重定向到宿主机 /home 的 inode，所以容器里写 /test 实际写的是宿主机 /home。

Dockerfile 的 ENTRYPOINT+CMD 关系容易混淆：完整启动格式是 `ENTRYPOINT CMD`，默认隐含 ENTRYPOINT 是 `/bin/sh -c`，所以 `CMD ["python","app.py"]` 实际跑的是 `/bin/sh -c "python app.py"`。做 Java 镜像时这个细节会影响信号传递——`sh -c` 启动的进程不是 PID=1，SIGTERM 传不到 JVM，优雅停机失效。正确做法是 exec 形式 `ENTRYPOINT ["java","-jar","app.jar"]`，让 JVM 直接当 PID=1。

对生产的启发：第一，dockerinit 先做 rootfs 准备、Volume 挂载、hostname 配置，再 execv 让应用进程接管 PID=1，这个两阶段启动模型解释了为什么 Volume 挂载点目录会被 commit 进镜像但内容不会；第二，Volume 不进 commit 是因为 Mount Namespace 隔离了挂载事件，宿主机看到的可读写层 /test 是空的；第三，`--net=host` 拆掉 Network Namespace 隔离墙，性能敏感场景（如 AI 训练的 NCCL 通信）常用，但安全上等于裸奔，要权衡。白话容器基础四篇读完，容器不再是黑盒——它就是一组 Linux 系统调用的组合应用。
