这一篇是整个容器原理的「任督二脉」：容器不是虚拟机里跑 Guest OS，而是宿主机上一个普通进程，只不过创建时加了 CLONE_NEWPID 等 Namespace 参数，让它「看」不到别的进程。`docker run -it busybox /bin/sh` 里 /bin/sh 的 PID=1 是障眼法，宿主机上它其实是 PID=100。

这个认知直接颠覆了那张流传甚广的「Docker Engine = Hypervisor」对比图。Docker Engine 不是 Hypervisor，它不创建任何实体「容器」，真正负责隔离的是宿主机内核本身。Docker 只是帮进程加了一组 Namespace 参数的「旁路辅助工具」——这就是后来 CRI/O、containerd 能取代 Docker 的根本原因：Docker 在这里的角色本来就是可替换的。

对 Java 后端的直接启发：JVM 早期版本（Java 8u131 之前）在容器里按宿主机内存算 MaxHeapSize，就是因为 JVM 读的是 /proc 里的宿主机信息，看不到 Cgroups 限制。理解了「容器是带视角的进程」，就能理解为什么 JVM 参数会失灵——进程视角被 Namespace 改了，但 JVM 的探测逻辑没跟上。做 AI 实操时同理：PyTorch DataLoader 的 num_workers 如果按宿主机 CPU 核数设，容器里会起过多进程导致调度抖动。所有「容器里行为异常」的坑，根源都是「进程以为自己看到了全世界，其实只看到 Namespace 限定的一块」。
