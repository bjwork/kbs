丁奇第 20 讲。幻读定义：**同一个事务里，后一次查询看到了前一次没看到的「新插入」的行**（update 不算，那是不可重复读）。即使给所有现有行加行锁，仍锁不住「还不存在的行」——所以 InnoDB 在可重复读下引入**间隙锁（gap lock）**，锁的是「行与行之间的间隙」，比如 (5,10) 这个区间不许插入。间隙锁之间不互斥（两个事务可同时持有同一间隙的 gap lock），真正冲突的是「插入意向锁」。问题：间隙锁只锁插入不锁更新，但它跟「插入意向锁」的冲突是死锁高发区。

**对我的价值**：把幻读和不可重复读区分开是面试必考，但**生产价值在于理解间隙锁为什么导致死锁**。经典案例：两个事务同时 select ... where id=5 for update（id=5 不存在），都拿到间隙锁，然后都 insert——互相等对方的间隙锁，死锁。排查这类死锁要看 show engine innodb status 里的 lock mode X locks gap before rec。

**立场**：间隙锁是「可重复读 + 防止 binlog 主从不一致」的工程妥协。如果只追求防幻读，串行化就够了；间隙锁是在**保证 binlog 重放正确性**的前提下做的最小让步。这解释了为什么很多 DBA 建议新业务直接用「读提交 + binlog row」——关掉间隙锁省下的死锁排查成本，比可重复读带来的语义优雅更划算。我在新库上现在默认 RC。
