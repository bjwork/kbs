这篇把 K8s 自定义控制器的执行引擎拆透了。Informer 是一个带本地缓存（Store）和索引（Indexer）的 client，通过 Reflector 的 ListAndWatch 机制把 APIServer 的对象同步到本地 Delta FIFO Queue，再更新缓存并触发 EventHandler。EventHandler 不直接跑业务，只把对象的 Key（namespace/name）丢进 workQueue；控制循环从队列取 Key，用 Lister 从缓存读期望状态，对比实际状态做 Reconcile。

我的判断：这套 Informer+workQueue 是 K8s 声明式 API 的执行骨架，所有控制器（含 Operator）都是同一套路。作为 Java 后端我类比成 Spring 事件总线+异步消费者，但 K8s 多了本地缓存这层，避免每次 reconcile 都打 APIServer，是工程上的关键优化。workQueue 的存在是为了解耦快慢任务——Informer 对事件响应极快，而 Reconcile（如建集群）很慢，没有队列慢任务会 block Informer。真正写业务时只需关注「期望 vs 实际」的 Reconcile，client/informer/lister 都是 codegen 自动生成的，这也就是为什么能看懂这套就能看懂任何 Operator。
