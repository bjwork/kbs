CAP 应用时最容易被误用的四个细节（来自 Brewer 2012 年的《CAP 理论十二年回顾》）：

**1. CAP 粒度是数据，不是系统**。同一系统里用户账号数据选 CP、用户资料数据选 AP 很正常。把整个系统强行限定 CP 或 AP 都顾此失彼。

**2. CAP 忽略网络延迟**。理论假设事务提交瞬间所有节点同步，实际上同机房几 ms、跨机房几十 ms。**所以完美 CP 物理上做不到**——对余额/库存这种强一致场景，「理论 CP」实际只能「单点写入+其他节点备份」的 CA。支付宝光缆挖断只有部分用户异常，就是按用户 ID 分区的结果。

**3. 没分区时 CA 都要保证**。CAP 只在分区时才有取舍，正常时既要 C 又要 A。不同数据实现 CA 的方式也不同——账号用消息队列（实时性可控）、用户资料用数据库同步（简单）。

**4. 「牺牲」不等于什么都不做**。分区时记录下未同步的操作日志，分区恢复后**用日志追平数据回到 CA**——AP 系统按「最后修改优先」「字数最多优先」等规则合并，或人工仲裁。

**ACID vs CAP vs BASE**：
- ACID 是**数据库事务**的理论，A=原子性、C=数据完整性——跟 CAP 的 A=可用性、C=节点一致性**完全不是一回事**，关公战秦琼。
- BASE（Basically Available / Soft State / Eventual Consistency）是 **CAP 中 AP 方案的延伸**：分区期允许损失部分可用性（保核心），允许中间状态（软状态），分区后最终一致。关键在「部分」「核心」「一定时间」「最终」四个词的具体定义，要按业务定。

**立场**：把「CAP 的 C 跟 ACID 的 C 不是一回事」讲透太重要了——太多文章混着讲。BASE 是 AP 的补丁这个定位也很准——AP 不是放弃一致性，是延迟一致性。「分区日志+恢复追平」是工程落地的关键细节，不谈这个 CAP 就永远停留在概念层。
