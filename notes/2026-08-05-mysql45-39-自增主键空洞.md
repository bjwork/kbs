丁奇第 39 讲。自增 id 空洞来源：①**唯一键冲突**——申请自增值后插入失败，自增值不回收；②**事务回滚**——同理，自增值已消耗；③**批量插入的预估申请**（insert ... select 一次申请一批用不完）；④自增锁的优化策略（innodb_autoinc_lock_mode=2 时并发插入各自拿值，语句间不保证连续）。8.0 前自增值存内存，重启后取 max(id)+1 可能回退；8.0 起持久化到 redo log。结论：**自增主键保证递增，不保证连续**。

**对我的价值**：「业务依赖自增 id 连续性」是个隐蔽的坑——我见过用 id 差值算「两条记录之间有多少条数据」的代码，在唯一键冲突后算错。还有用 id 做分片路由 key 的，空洞导致分片不均。正确姿势：**自增 id 只当「有序的标识符」用，不当「连续的序号」用**；要连续序号，用单独的发号器或业务字段。

**立场**：innodb_autoinc_lock_mode=2 + binlog row 是作者的推荐，也是现在的事实标准。但值得记一下为什么这么配——lock_mode=2 是「语句级」申请（轻量），但 statement 格式 binlog 下会导致主备 id 不一致（并发插入顺序不同）；row 格式记的是行变更不记 id 分配过程，所以安全。**性能优化和正确性经常是绑在一起卖的**，单看一个参数会踩坑。
