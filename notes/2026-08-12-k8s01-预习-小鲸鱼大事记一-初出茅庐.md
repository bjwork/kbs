这一篇的核心洞察：Docker 技术上没黑科技，和 Cloud Foundry 一样用 Cgroups + Namespace，唯一的差别是 Docker 镜像打包了整个操作系统的文件和目录，而不是只打包应用可执行文件 + 启停脚本。就这一点，把 PaaS 最痛的「本地能跑上云就跪」彻底解决了。

我做过类似 PaaS 的打包脚本，深有体会——为每种语言、每个框架版本维护 buildpack 是地狱。Docker 的解法粗暴但有效：直接把 CentOS/Ubuntu 的根文件系统塞进压缩包，本地和云端解压出来就是同一个环境。这其实是把「依赖」的定义从「语言层」下沉到「操作系统层」，一步到位。

对技术选型的启示：解决根本性问题（应用打包）的简单方案，胜过解决衍生问题的复杂方案。Cloud Foundry 在 buildpack 上不断加语言支持是治标，Docker 用一个统一压缩包格式治本。做 Java 后端选型时同理——别在配置漂移上打补丁，用不可变镜像一步到位。dotCloud 改名 Docker 公司这个动作也埋了伏笔：把开源项目名变成公司商标，日后跟社区撕扯的种子这时候就种下了。
