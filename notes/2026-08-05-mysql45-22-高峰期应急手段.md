丁奇第 22 讲。业务高峰的应急手段：①**短连接风暴**——连接数打满时，先 kill 空闲连接腾位（show processlist 里 Sleep 的），根治靠连接池 + 长连接；②**慢查询应急三招**：kill 慢查询会话、用 force index 或改写 SQL 绕过、最狠的是**在 proxy 层做语句重写**（把导致问题的 SQL 直接改写或熔断）；③**事先预防**——上线前 SQL 审计、索引评审、测试环境压测。作者明示这些都是「饮鸩止渴」，临时方案各有风险。

**对我的价值**：「kill 空闲连接」这个操作要克制——kill 掉的是事务未提交的连接会触发回滚，回滚大事务比连接打满更伤。正确顺序：先 kill 明确空闲的 Sleep 连接，再考虑kill 慢查询，事务中的连接最后动。语句重写是核选项，proxy 层改 SQL 等于在运行时改业务逻辑，必须有审批和回滚预案。

**立场**：这篇的价值不在技术细节，在**作者承认「无损方案不存在」**。高峰期续命本质上都是在不同风险之间选：kill 连接有损一致性，语句重写有损正确性，限流有损可用性。架构师的功力体现在**事前把「无损方案」做完**（容量规划、SQL 审计），而不是事后的花式救火。我把这篇当「技术债利率表」用——每个应急手段都标好了代价。
