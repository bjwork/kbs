丁奇第 17 讲。`order by rand()` 要建临时表 + filesort，给每行算一个随机数再排序——表越大越慢，没有索引可救。优化方案递进：①应用层先 count 出总数 N，随机一个偏移量再 limit offset,1（两次查询，扫 N 次索引但只有一行回表）；②主键有洞不行时用 min/max 区间随机 + where id>=R limit 1（有偏但快）；③要取 3 条就随机 3 个偏移量（总扫描 C+(Y1+1)+(Y2+1)+(Y3+1)）。

**对我的价值**：核心启示是「随机」这个需求数据库天然不擅长，正确姿势是**把随机性挪到应用层**。作者的落脚点更广——「尽量将业务逻辑写在业务代码中，让数据库只做读写数据」，这句话反对的是在 SQL 里写花活（stored procedure / 复杂函数），跟我和团队争论「业务逻辑放哪层」时的立场完全一致：数据库做计算，扩展性就是单机的；挪到应用层，扩容是水平的。

**立场**：方案①的偏移量法在「主键连续」假设下才均匀——实际表必有空洞，所以它是「近似随机」。多数业务（推荐、抽签）够用；但**不能用在抽奖类要证明公平性的场景**，那种场景宁可慢一点用密码学随机源在应用层选 ID 列表。技术方案的正确性边界，比方案本身重要。
