丁奇第 10 讲。优化器选索引靠两样东西：扫描行数估算 + 是否回表/排序等代价。扫描行数来自**索引统计信息（cardinality）**——它不是精确值，是采样 N 个页算的平均值乘以页数，默认采样 20 页（innodb_stats_persistent_sample_pages）。所以大表数据分布一变，统计没跟上，优化器就会选错。解法三板斧：analyze table 重新统计；force index 强制指定；改语句引导（比如把 order by b limit 1 改成 order by b,a limit 1 消除排序代价误判）。

**对我的价值**：理解了「统计是采样」就理解了为什么选错索引总发生在**大表 + 数据倾斜**场景——采样 20 页对均匀分布够用，对倾斜分布就是盲人摸象。我处理过一次线上事故：一条 0.01s 的查询某天突然变 30s，执行计划全变，最后 analyze table 解决。当时只记住了这个命令，这篇把为什么补上了。

**立场**：force index 是创可贴不是药——索引名硬编码在 SQL 里，以后重构表结构全是雷。我的排序：analyze table > 改语句引导 > 删多余索引 > force index。另外作者的坦白值得尊敬：「今天后面几个例子没展开原理，因为我也没完全搞懂优化器内部逻辑」——承认边界比假装全知可信得多。
