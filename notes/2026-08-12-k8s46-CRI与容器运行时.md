CRI/SIG-Node 下篇，深入 CRI 接口设计。两组接口：RuntimeService（容器生命周期：创建/启动/删除/exec）和 ImageService（镜像拉取/删除）。核心设计原则：CRI 只关注容器，不关注 Pod——因为 Pod 是 K8s 编排概念不是容器运行时概念，硬塞进 CRI 会让 Pod API 字段一变 CRI 就得跟着变。但有个 RunPodSandbox 接口，它不是 Pod 对象，是 Pod 里跟运行时相关字段的子集（HostName/DnsConfig/CgroupParent），具体怎么实现 Pod 模型由容器项目自己定。Docker 的 dockershim 用 pause 容器（Infra 容器）hold 住 Network Namespace；Kata Containers 直接起轻量 VM 当 Pod。RunPodSandbox 里还会调 networkPlugin.SetUpPod，即 CNI 插件的 add 方法给 Pod 配网络。

Streaming API（exec/logs）设计很巧：CRI shim 不直接处理，而是返回一个 Streaming Server 的 URL 给 kubelet，kubelet 再 Redirect 给 apiserver，apiserver 重定向到 Streaming Server 建长连接。这样长连接数据不经过 kubelet 转发，性能好。

我的判断：CRI 接口设计宽松是优点不是缺陷——给了容器项目高自由度，Kata/gVisor/虚拟机这种"非典型"容器都能无缝接入，这才是插件化该有的样子。对比 CNI 的接口设计（同样宽松，只有 ADD/DEL/CHECK），CRI 的宽松让 K8s 不被任何单一容器技术绑架。实战建议：对容器层有特殊需求（安全隔离、自定义运行时）优先实现 CRI shim，别改 kubelet。Device Plugin 分配的 GPU 信息是通过 CreateContainer 的 devices 字段传给 dockershim 的——这把 44 篇的 Device Plugin 和这里的 CRI 串起来了。
