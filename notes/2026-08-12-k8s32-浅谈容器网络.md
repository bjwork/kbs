这篇讲单机容器网络原理。容器有独立 Network Namespace（网卡/回环/路由表/iptables），要通信就要「出」Namespace。核心机制：Veth Pair 是成对虚拟网卡，一端在容器里当 eth0，另一端在宿主机上「插」到 docker0 网桥上。网桥是二层交换机，按 MAC 地址学习转发。容器 A ping 容器 B 时：A 的 eth0 发 ARP 广播找 B 的 MAC，数据包经 Veth Pair 到宿主机端的虚拟网卡（已降级为网桥端口，无协议栈资格），流入 docker0，docker0 查 CAM 表转发到 B 对应的端口，进入 B 的 Namespace。容器访问外网则经 docker0 到宿主机路由表，再走宿主机 eth0。

我的判断：容器网络本质是 veth pair + bridge，这是 debug 容器网络不通的基础。遇到容器连不通，先 ping docker0 网桥，再查 docker0 和 veth 设备相关的 iptables 规则，基本能定位问题——这个排障路径比盲目重启容器高效得多。作为 Java 后端我类比成 Spring 的 ApplicationContext 隔离：每个容器有自己的「网络上下文」，Veth Pair 是跨上下文的桥接器。跨主机通信靠 Overlay Network——在宿主机网络上用软件构建覆盖网络，把所有容器连通，Flannel/VXLAN/CNI 都是这个思路。文章没深入跨主机细节（留到后续），但把单机基础打牢了：理解了「Veth Pair 是网线、docker0 是交换机、容器是独立主机」，后面看 CNI 插件就是在这个基础上加隧道或路由。hostNetwork 模式性能好但端口冲突，生产用要做好端口规划。
