丁奇第 38 讲。Memory 引擎（内存表）数据只存内存，重启丢光。问题链：备库重启 → 内存表空 → 主备同步线程报错停；双 M 架构下更惨——主库重启后内存表空，但**delete 语句会同步到备库把备库数据也删了**。另外 Memory 不支持行锁（只有表锁），更新会阻塞查询，高并发下未必比 InnoDB 快。唯一存活场景：**内存临时表**（上一讲的 group by 临时表默认 Memory 引擎，因为临时表会话私有、不需要持久化、hash 索引正好用）。

**对我的价值**：「双 M + Memory 表」的数据删除陷阱值得所有 DBA 背下来——主库重启丢数据是存储层的事，但**它通过 binlog 把「空」状态传染给了备库**，这是架构层的灾难。这解释了为什么 RDS 厂商基本都不让用 Memory 引擎。InnoDB 的 Buffer Pool 已经把热数据缓存得很好了，Memory 引擎的性能优势在现代硬件上被高估。

**立场**：作者结论「生产不建议用普通内存表」我举双手同意。但我补一个视角：**Memory 引擎的失败不是内存存储的失败，是「内存存储没有独立的高可用方案」的失败**。Redis 能活得好，是因为它有自己的持久化（RDB/AOF）和主从体系；Memory 引擎寄生在 MySQL 的主从体系上，而这个体系是按磁盘存储设计的，水土不服是必然的。
