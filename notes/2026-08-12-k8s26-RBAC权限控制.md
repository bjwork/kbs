这篇把 K8s 授权体系讲清楚了。核心三件套：Role（权限规则列表）、Subject（被作用者，User/Group/ServiceAccount）、RoleBinding（绑定关系）。Role/RoleBinding 是 Namespace 级，ClusterRole/ClusterRoleBinding 是集群级。实战中最常用的是 ServiceAccount——K8s 自动给它发 Token（Secret），Pod 声明 serviceAccountName 后 token 自动挂到 /var/run/secrets/kubernetes.io/serviceaccount，容器用这个 token 访问 APIServer，权限受绑定的 Role 约束。

我的判断：RBAC 是 K8s 多租户安全的基础，Role/ClusterRole 绑定粒度直接决定泄露半径。文章里有个反直觉的点——默认 ServiceAccount 没绑 Role 时反而有大部分权限，这其实是个安全隐患，生产环境务必给每个 Namespace 的 default SA 绑只读 Role。作为 Java 后端，我把 ServiceAccount 理解成 Spring Security 里的 service-to-service 凭证，但 K8s 的精妙在于权限规则可以细化到 resourceName 级别（如只允许 get 某个 ConfigMap），这点比很多业务系统的 RBAC 还细。内置的 cluster-admin 是 verbs=* 的核武器，用之前三思。system: 开头的 ClusterRole 是给系统组件用的，如 system:kube-scheduler 绑给 kube-scheduler 的 SA，这套「组件也是 SA」的设计让系统组件和用户应用走同一套授权模型，统一且可审计。
