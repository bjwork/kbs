K8s 里每个 API 对象在 Etcd 的资源路径由 Group/Version/Resource 组成，核心对象（Pod/Node）Group 为空走 /api，非核心（CronJob）走 /apis/<group>/<version>/<resource>。APIServer 处理流程：过滤授权 → MUX/Routes 路由 → 按类型定义 Convert 成 Super Version（全字段全集）→ Admission（Initializer/Admission Controller）→ Validation → Registry 注册 → 序列化存 Etcd。CRD（Custom Resource Definition）让用户自定义新 API 资源类型，配 Go 代码生成（types.go+code-generator）自动产出 clientset/informer/lister。

**我的判断**：CRD 是 K8s 从「容器编排器」升级成「分布式应用平台底座」的关键一跃。只有内置 Pod/Deployment 时，K8s 只是个编排器；有了 CRD，任何人都能往 K8s 加「Network」「MySQLCluster」「TrainingJob」这种自定义资源，再用自定义控制器实现业务逻辑——这就是 Operator 模式的基础。我见过 Prometheus Operator、Argo Rollout 都靠 CRD 扩展 K8s，本质上是把领域知识（怎么部署一个高可用 Prometheus、怎么做金丝雀发布）编码成 K8s 原生 API 对象。G/V/R 寻址这个设计也值得品味：同一种资源多版本共存（v1beta1 → v1）靠 Super Version 做转换，向后兼容内置在 API 层，这比硬编码版本判断优雅得多。APIServer 自动生成代码曾占 K8s 总代码 20%-30%，说明声明式 API 的工程成本不低——但这个成本换来的是所有控制器、客户端都能用统一范式操作任意资源，包括用户自定义的，这笔账划得来。
