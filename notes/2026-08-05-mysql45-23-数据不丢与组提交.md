丁奇第 23 讲。WAL 的「数据不丢」前提是日志真落盘。redo log 三层：redo log buffer（内存）→ page cache（OS）→ 磁盘。innodb_flush_log_at_trx_commit：0 每秒刷、1 每事务刷（最安全）、2 每事务只到 page cache（OS 崩才丢）。binlog 类似：write 到 page cache，fsync 才落盘，sync_binlog=1 每事务 fsync。性能优化的关键是**组提交（group commit）**：攒一波事务一起刷盘，把多次 IOPS 合并成一次，日志并发度越高单次刷盘摊得越薄。

**对我的价值**：「write 和 fsync 的区别」值得所有后端背——write 只到 OS 的 page cache，进程崩了数据还在，机器断电才丢；fsync 才真正到磁盘。所以「双 1」配置保的是机器断电也不丢，代价是每事务一次磁盘 IO。组提交是这个代价的缓解：**并发越高，单次 fsync 摊薄的事务越多**——这解释了为什么 MySQL 在高并发下反而「双 1 也扛得住」。

**立场**：「双 1 是必须的」这结论我同意，但作者没展开的一个现实是——**云数据库时代这个决策被 RDS 厂商替你做了**，多数云 MySQL 默认就是双 1 且不可调。自建库才需要真正理解这三层缓冲。学习价值依然满格：这套「内存 buffer → OS cache → 磁盘」三层模型是所有存储系统的通用结构（Kafka、ES、LevelDB 全一样），吃透一个处处可用。
