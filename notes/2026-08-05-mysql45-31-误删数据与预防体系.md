丁奇第 31 讲。误删场景：delete/update 忘加 where、drop table、truncate、rm 数据文件。恢复手段：①**binlog 回滚**——delete 的逆操作是 insert（row 格式 binlog 记了删除前的整行），用 binlog2sql / my2sql 生成反向 SQL；②**全量备份 + binlog 重放**到误删前一刻；③**延迟备库**（故意让备库延迟 N 小时，误删后从延迟备库捞数据）。预防体系：权限分离（业务账号不给 drop 权限）、SQL 审计（上线前审查）、**改名代替删除**（drop 前先 rename 成 _to_be_deleted，观察一周再删）、定期恢复演练。

**对我的价值**：「改名代替删除」这条我现在强制执行——所有要 drop 的表先 rename 加后缀，进「停尸间」观察期。真正的 drop 权限只有 DBA 有，且要走工单。这个简单动作挡住了我们团队至少三次误删。延迟备库是更高级的保险，但成本是一个实例 + N 小时存储，只有核心库值得配。

**立场**：「预防远比处理重要」是陈词滥调，但作者把它落成了具体动作清单，这就有价值了。我补一条他没强调的：**恢复演练必须定期做**。备份方案没被验证过等于没有备份——我见过太多团队第一次恢复是在真实故障时，结果发现 binlog 断了、备份文件损坏、恢复脚本依赖的 Python 版本不对。恢复能力是一个需要演练维持的系统，不是一个配置项。
