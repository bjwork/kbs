丁奇第 45 讲，收官篇。四种自增 id 到上限的行为：①**表自增 id**（int unsigned 上限 42 亿）——到顶后不再变，插入报主键冲突，**业务直接停摆**；②**row_id**（InnoDB 隐藏主键，6 字节）——到顶归 0 重新来，**后写的覆盖先写的**，数据静默丢失；③**Xid**（redo log/binlog 的事务 ID）——理论上会重复，概率极小；④**thread_id**（show processlist 的 ID）——4 字节，到顶归 0，新连接覆盖旧连接的 thread_id，kill 可能杀错人。

**对我的价值**：「int 主键够用吗」是每个表设计都要回答的问题。42 亿看着多，但**大表 + 空洞多**（唯一键冲突、回滚）的业务，几年就能跑满。我的规范：**核心表一律 bigint**（8 字节，上限是 int 的 40 亿倍，有生之年用不完）。row_id 归 0 覆盖数据这个最吓人——没有主键的表 InnoDB 自动生成 row_id，而 row_id 是全局递增的，大表到顶后新数据覆盖老数据，无声无息。**永远显式定义主键**。

**立场**：这篇作为收官很妙——把「自增」这个看似简单的概念拆出四种实现、四种失败模式。它提醒我**任何「无限」的抽象都有物理边界**，而边界的失败模式各不相同：有的报错（表自增 id），有的静默丢数据（row_id），有的可能误伤（thread_id）。做系统设计时，对每个计数器问一句「到顶了会怎样」，是最便宜的鲁棒性检查。
